# 03. 배포 전략: QA 및 Production 환경

이 문서는 QA(테스트) 및 Production(운영) 환경에 애플리케이션을 배포하기 위한 표준적인 전략을 안내합니다.

## 1. 핵심 전략: "Build Once, Deploy Anywhere"

-   **동일한 아티팩트**: 어떤 환경에 배포하든, 항상 **동일한 코드와 동일한 Docker 이미지**를 사용합니다.
-   **환경별 설정 분리**: 각 환경(QA, Prod)의 차이점(예: DB 주소, API 키)은 오직 **환경 변수**를 통해서만 주입됩니다.

## 2. QA 환경 (Staging/Testing)

QA 환경은 실제 운영 환경과 유사하게 구성된, 여러 개발자와 테스터가 공유하는 중앙 테스트 서버입니다.

-   **데이터베이스**: QA 팀 전용으로 독립된 데이터베이스 서버(예: AWS RDS의 테스트 인스턴스)를 사용합니다.
-   **환경 변수 주입 방법**:
    -   **CI/CD 파이프라인 (권장)**: Jenkins, GitHub Actions, GitLab CI 등의 자동화 도구를 사용합니다.
    -   파이프라인은 빌드 시 **QA 환경용 Secret 저장소**(예: GitHub Secrets)에서 DB 접속 정보(`POSTGRES_HOST`, `POSTGRES_USER`, `POSTGRES_PASSWORD` 등)를 안전하게 가져옵니다.
    -   가져온 환경 변수들을 컨테이너 실행 시점에 주입하여 애플리케이션을 배포합니다.
    -   **수동 설정**: 간단한 환경에서는 QA 서버에 직접 접속하여 `/etc/environment` 또는 셸 프로필(`.bashrc`)에 환경 변수를 미리 설정해 둘 수도 있습니다.

## 3. Production 환경 (Live)

Production 환경은 **보안, 안정성, 가용성**을 최우선으로 고려해야 합니다.

-   **데이터베이스**: 고가용성 및 백업이 보장되는 운영 데이터베이스 클러스터(예: AWS RDS Multi-AZ)를 사용합니다.
-   **민감 정보 관리 (Secrets Management)**:
    -   DB 비밀번호, 외부 API 키 등 모든 민감 정보는 **AWS Secrets Manager**, **Azure Key Vault**, **HashiCorp Vault**와 같은 전문 Secret 관리 도구에 암호화하여 저장합니다.
    -   **절대로** 일반 환경 변수나 파일에 민감 정보를 저장하지 않습니다.

### 운영 환경 배포 흐름 예시 (AWS 기준)

1.  **Secret 저장**: 운영 DB의 접속 정보를 **AWS Secrets Manager**에 저장합니다.
2.  **권한 부여**: 애플리케이션이 실행될 컨테이너 환경(예: AWS ECS, EKS)에 해당 Secret을 읽을 수 있는 **IAM Role**을 부여합니다.
3.  **애플리케이션 실행**:
    -   애플리케이션 컨테이너가 시작됩니다.
    -   애플리케이션은 내장된 AWS SDK를 통해, 자신에게 부여된 IAM Role 권한을 사용하여 Secrets Manager에 직접 접속합니다.
    -   DB 접속 정보를 **메모리로 안전하게** 불러와 데이터베이스 연결에 사용합니다.
4.  **보안**: 이 방식을 통해 민감 정보가 코드, 서버 파일, 환경 변수 어디에도 노출되지 않으므로 최고 수준의 보안을 유지할 수 있습니다.

이러한 전략을 통해 개발부터 운영까지 일관되고, 안전하며, 자동화된 배포 파이프라인을 구축할 수 있습니다.
